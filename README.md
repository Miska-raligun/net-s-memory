# 互联网记忆（net-s-memory）

**在内容被删除之前把原文存下来，删除之后还能证明它存在过、证明它没被改过，而且不依赖任何人运营的服务器。**

这是一个浏览器扩展。你在读一篇文章时点「存档」，扩展会在本机保存正文、截图和原始 HTML，
计算正文的 SHA-256，并把这个哈希锚定到比特币时间戳上。你愿意的话，还可以把一条签名的
「见证」发布到 Nostr 中继。之后原文如果被删、被屏蔽，你和其他人都能拿出副本，
并且任何人都能独立验证：

- 这段正文在某个比特币区块之前就已经存在（OpenTimestamps）；
- 有多少互不相关的人存到了**同一个正文哈希**；
- 有谁、在什么时候看到它消失了。

## 为什么不用中央服务器

这个项目最初是一个中心化网站（见下方「旧后端」），由服务器抓取新闻、签名、写入 Merkle 日志。
那套设计有一个根本问题：**运营方本人就是单点**。运营方可能被施压删除内容，服务器可能被查封，
域名可能被封锁；而且运营方重写整份日志后重新签名，网站自带的「验证」按钮照样显示通过。

所以现在改成了扩展：

| 需求 | 现在的做法 |
| --- | --- |
| 存得下 | 每个用户在自己的浏览器里存原文，不需要服务器 |
| 证明没被改过 | 多个独立的人见证同一个正文哈希，外加比特币时间戳；不信任任何单一签名者 |
| 知道被删了 | 用户访问时识别删帖页面，扩展定期回访存过的链接；删除观察作为签名事件公开 |
| 没人运营也能活 | 只用公共基础设施：Nostr 中继、OpenTimestamps 日历、Internet Archive，以及可选的 Blossom 文件服务器，都可以任意替换 |

## 威胁模型

**防得住：**

- **原文被删除、被屏蔽、被悄悄修改**：本机有副本，比特币时间戳证明它更早存在，正文哈希证明副本没改过。
- **某个见证人造假**：别人重新计算哈希就能发现。改了正文再重新签名的见证，会作为「另一个版本」单独显示，
  不会和原文混在一起。
- **某个中继删数据或下线**：见证会发到多个中继，副本也在每个见证人的本机。
- **项目维护者消失**：扩展本身不依赖这个仓库的任何服务。

**防不住（或只能部分缓解）：**

- **女巫攻击**：密钥可以随意生成，所以「N 人见证」本身不能证明真实性。界面会单独标出你关注的人，
  以及与你自己副本一致的版本；用的人越多、信任网络越密，这个问题越小。
- **第一个存档的人就拿到了被改过的页面**：如果每个见证人看到的都是篡改过的版本，扩展无从知道。
  能起到交叉印证作用的是 Internet Archive 快照，以及「查找其他报道」（Google / 必应，默认隐藏境内来源）。
- **使用者自身的风险**：
  - 发布见证或删除观察，等于公开「这个公钥看过这条内容」。
  - 默认什么都不发布，所有发布都要手动操作。
  - 建议使用不和真实身份关联的专用 Nostr 密钥。
  - 截图和 HTML 可能带有你的登录信息，所以默认不上传。
  - 「查询网络见证」会让中继知道你在看哪个链接，所以只在你点击时才查询。
- **扩展商店下架**：需要同时发布 Firefox 版本，并提供 crx 文件直接下载。

## 它是怎么工作的

```
读文章 ──► 存档本页 ──► 正文抽取 → 规范化 → SHA-256
                          │
                          ├─ 本机保存：正文 / 截图 / HTML
                          ├─ OpenTimestamps：锚定正文哈希（只发送加盐哈希）
                          ├─ Internet Archive：第三方快照（可选）
                          └─ 加入监测：定期回访（1 小时 … 90 天）
                                │
发布见证（手动）──► Nostr kind 1909：r=URL, x=正文哈希, 正文内联或放在 Blossom
原文消失 ──► 徽章变红 / 图标角标 ──► 发布删除观察（手动）kind 1910
查询网络见证 ──► 按正文哈希分组显示各版本 ──► 必要时导入他人副本（导入前重新校验）
```

### 独立验证一份存档

在「我的存档」里下载正文（`.txt`）和 `.txt.ots`：

```bash
sha256sum <id>.txt          # 结果应等于见证里的 text_sha256
ots verify <id>.txt.ots     # 证明这段正文在对应比特币区块之前就已存在
```

## 事件格式

其他客户端可以照着下面的格式实现，与本扩展互通。

- **正文规范化 `nsm-text-norm.v1`**：
  - 先做 Unicode NFC；
  - 去掉零宽字符、BOM 和软连字符；
  - 各种空白统一成普通空格，各种换行统一成 `\n`；
  - 每行内的连续空格合并，并去掉行首尾空格；
  - 删除空行，各行用 `\n` 连接。
  - `text_sha256` 是规范化后正文 UTF-8 字节的 SHA-256。
- **见证（kind 1909，普通事件）**：
  - 标签：`["r", 规范化 URL]`、`["x", text_sha256]`、`["t", 域名]`、`["alt", …]`。
  - content 是 JSON，`schema` 为 `"nsm-capture.v1"`。正文不超过 32 KB 时直接放在 `text` 字段里；
    超过时，`blobs` 里必须有一个 `kind: "text"` 的 Blossom 引用。
  - 接收方必须验签，核对标签和内容一致，并对内联正文重新规范化、重新计算哈希，
    任何一项不一致都拒收。
- **删除观察（kind 1910，普通事件）**：
  - 标签：`["r", URL]`、`["s", 状态]`，以及可选的 `["x", 最后见过的正文哈希]`。
  - 状态取值：`live`（在线）、`deleted`（已删除）、`censored`（被屏蔽）、`restricted`（设为不可见）、`not_found`（页面不存在）。
  - content 的 `schema` 为 `"nsm-observation.v1"`；`observed_at` 晚于事件创建时间的观察会被拒收。
- **Blossom**：按 BUD-01/02 上传文件，下载后必须核对 SHA-256。

### 安装发布版

到 [Releases](https://github.com/Miska-raligun/net-s-memory/releases) 下载最新的
`net-s-memory-extension-vX.Y.Z.zip`（可用同名 `.sha256` 文件校验），解压到一个固定的文件夹。
然后打开 `chrome://extensions`，开启「开发者模式」，点「加载已解压的扩展程序」，选择解压出的文件夹。

发新版本（任选一种）：

- 在 GitHub 网页上依次进入 Releases → Draft a new release，新建标签 `vX.Y.Z`，目标选 main，然后 Publish；
- 或者给 main 上的提交打 `vX.Y.Z` 标签并推送。

两种方式都会触发 `.github/workflows/release-extension.yml`：自动测试、构建，把 zip 和 `.sha256` 附到 Release 上，
并把标签里的版本号写进扩展的 manifest。

### 开发

```bash
cd extension
npm ci
npm run test        # 单元测试
npm run build       # 产物在 dist/
```

在 Chrome 中打开「扩展程序」页面，开启「开发者模式」，点「加载已解压的扩展程序」，选择 `extension/dist/`。
LLM key 是可选的，只用于折叠起来的「信源参考信号」，存档和见证功能都不需要它。

## 旧后端（已冻结）

`backend/`（FastAPI + Postgres）、`web/`（Next.js）、`infra/` 是项目最初的中心化版本：
服务器抓取并用 LLM 选稿，用服务密钥签名，写入 RFC 6962 Merkle 日志，再锚定到 OpenTimestamps。
冻结的原因是：

- **没有保存原文**：签名的对象是 LLM 写的摘要和一组链接，原文一删，就只剩死链。
- **抗篡改对运营方无效**：浏览器验证用的证明和树根来自同一台服务器，没有对外的一致性证明，也没有外部见证，
  运营方重写整份日志后验证照样通过。
- **依赖一个需要长期运营的中心**。

这部分代码可以运行，CI 仍然覆盖它。其中唯一还和扩展有关的是 `backend/app/bridge/`：
它可以把旧数据转发成 Nostr 事件，默认不开启。
